Relationships may reference anchors owned by other domains (Infrastructure,
Data Platform, Workflow/Process) where a genuine cross-domain relationship
exists. Per the reverse-pointer rule in 00-framework/relation-types.md,
every cross-domain relationship below has a matching reverse pointer added
to the target domain's Ontology file.

## Agent Definition & Scope

- `harness-agent` --[requires]--> `harness-capability-scope`
  Rationale: an agent cannot be run without a defined boundary on what it's permitted to do.
- `harness-capability-scope` --[constrains]--> `harness-tool-permission-scope`
  Rationale: the capability scope's boundary limits what tools can be granted within it.
- `harness-agent` --[requires]--> `harness-model-version-pin`
  Rationale: an agent's behavior is only meaningfully evaluable and reproducible against a specific, pinned model version.
- `harness-agent` --[runs-on]--> `infra-model-serving-node`
  Rationale: cross-domain — an agent's model inference executes on a Model-Serving Node.
- `harness-agent` --[consumes]--> `infra-inference-workload`
  Rationale: cross-domain — running an agent is, at the compute layer, an Inference Workload.

## Prompting & Context Management

- `harness-prompt-template` --[produces]--> `harness-system-prompt`
  Rationale: a system prompt instance is typically generated by filling in a version-controlled template.
- `harness-agent` --[requires]--> `harness-system-prompt`
  Rationale: an agent needs a system prompt to establish its role and constraints before acting.
- `harness-context-window-budget` --[constrains]--> `harness-retrieval-source`
  Rationale: the budget allocated to retrieval results limits how much a retrieval source can contribute to one run.
- `harness-retrieval-source` --[requires]--> `dp-database`
  Rationale: cross-domain — a retrieval source is commonly backed by a queryable Database.

## Guardrails & Safety Controls

- `harness-action-allowlist` --[constrains]--> `harness-tool-permission-scope`
  Rationale: the allowlist/denylist is a finer-grained constraint underneath the coarser tool permission grant.
- `harness-rate-limit` --[constrains]--> `harness-agent`
  Rationale: a rate limit bounds how much action an agent can take in a given window.
- `harness-hitl-gate` --[produces]--> `harness-approval-gate`
  Rationale: each time a human-in-the-loop gate is reached and resolved, it produces one recorded approval gate decision.

## Observability & Evaluation

- `harness-agent` --[produces]--> `harness-trace`
  Rationale: every agent run produces its own trace/transcript record.
- `harness-eval-suite` --[requires]--> `harness-model-version-pin`
  Rationale: an eval suite's results are only valid against the specific pinned model version they were run against.
- `harness-eval-suite` --[produces]--> `harness-eval-metric`
  Rationale: running an eval suite produces one or more measured metric results.
- `harness-behavioral-drift` --[measured-by]--> `harness-eval-metric`
  Rationale: drift is detected as a change in eval metric results over time, without a model version change.
- `harness-cost-per-task` --[requires]--> `infra-inference-workload`
  Rationale: cross-domain — cost-per-task is derived from the measured Inference Workload an agent consumed to complete a task.

## Escalation & Human-in-the-Loop

- `harness-agent` --[requires]--> `harness-escalation-path`
  Rationale: an autonomous-capable agent needs a defined path for what it cannot resolve on its own.
- `harness-escalation-path` --[requires]--> `harness-hitl-gate`
  Rationale: an escalation path routes to a human-in-the-loop gate as its resolution mechanism.
- `harness-override` --[constrains]--> `harness-guardrail`
  Rationale: a logged break-glass override modifies normal guardrail enforcement for that one instance.
- `harness-eval-suite` --[consumes]--> `harness-agent-incident`
  Rationale: an agent-caused incident is a candidate source of a new eval suite test case.
